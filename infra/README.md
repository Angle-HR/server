# OpenHR infrastructure (Terraform)

Status: staging and production stacks written. Staging has passed `terraform validate` locally; **nothing has been planned or
applied in AWS**, and the production stack has not been through `validate` yet (written without Terraform available;
only HCL syntax and a module-argument cross-check were run). Expect a round of `init/validate/plan` fixes.

```
infra/
  bootstrap/            once per AWS account: state bucket + GitHub OIDC provider
  modules/              network, rds, redis, ecs_service, ecs_job, alb, edge (CloudFront+WAF+S3), uploads,
                        secrets, iam, ecr, dns, acm_cert, github_deploy, satellite_region
  envs/staging/         full staging stack (single region, collapsed topology)
  envs/production/      home region + four peered satellite regions (eu, us, asia, africa)

  CODE_CHANGES.md       app / Dockerfile / CI changes this infra depends on
```

## First deploy of staging (order matters)

1. **Bootstrap** (staging AWS account credentials): `cd bootstrap && terraform init && terraform apply`.
   Note the `state_bucket` output.
2. `cd envs/staging`; `cp backend.hcl.example backend.hcl` (fill account id); `cp terraform.tfvars.example terraform.tfvars`;
   `terraform init -backend-config=backend.hcl`.
3. **DNS first**: `terraform apply -target=module.dns`. Add the printed `route53_name_servers` as NS records for
   `staging.tryopenhr.com` in the parent zone. Wait until `dig NS staging.tryopenhr.com` answers.
4. `terraform apply` with `services_enabled = false`. Creates everything except running tasks (certificates validate
   once delegation works, which can take a few minutes).
5. **Set secret values** (Terraform created them empty; DSNs are written by Terraform):
   ```
   aws secretsmanager put-secret-value --secret-id openhr/staging/JWT_SECRET --secret-string "$(openssl rand -base64 48)"
   # AES-256 key ring, first key seals, all open. Format: v1:<base64 of 32 bytes>
   aws secretsmanager put-secret-value --secret-id openhr/staging/ANGLEHR_UK_SENSITIVE_KEYS --secret-string "v1:$(openssl rand -base64 32)"
   ```
   Use `terraform output secret_names` for the full list. TOTP_ENCRYPTION_KEY, ANGLEHR_REAPPLY_HMAC_KEY (32+ chars),
   R2_ACCESS_KEY / R2_SECRET_KEY (see CODE_CHANGES #3), SMTP_USER / SMTP_PASSWORD (Brevo),
   FLUVIO_BASIC_AUTH_*, ADMIN_BOOTSTRAP_PASSWORD. **Back up the SENSITIVE_KEYS** somewhere safe: losing them makes
   sealed special-category answers unreadable.
6. Make the CI changes in `CODE_CHANGES.md`, push images tagged with the git sha to ECR, set `image_tag`.
7. **Run migrations** (creates the five regional DBs + global): `aws ecs run-task` using `terraform output migrate_run_task`.
8. Set `services_enabled = true`, `terraform apply`. Then deploy the frontends to the two `frontend_buckets` and invalidate CloudFront.

## Things that will surprise you

- **ECS tasks fail to start if any referenced secret has no value.** That is why `services_enabled` exists.
- **Staging is started and stopped by hand**, not on a schedule: `scripts/staging-power.sh stop` disables the job schedules,
  scales ECS to 0 and stops RDS; `start` reverses it. NAT, ALB, Redis and WAF keep billing while stopped. RDS auto-restarts
  after 7 days stopped, so stop it again if staging sits idle that long. `terraform apply` restores `desired_count` and
  re-enables schedules, so run `stop` again afterwards if staging should stay off.
- The DB master password is generated by Terraform and is in state. Treat the state bucket as secret.
- Image tags are immutable in ECR: never push `latest`.
- `ops_allowed_cidrs` empty means the Fluvio dashboard host is unreachable (by design).

## Rough staging cost (not from the AWS calculator; check it)

About **$175/month** running 24/7 (London list prices, 18 Oct 2026): Fargate ~$58 (ClamAV 0.5 vCPU / 2 GB ~$25,
API + worker + dashboard ~$31, jobs ~$6), RDS t4g.small + 20 GB ~$29, ALB ~$20, Redis t4g.micro ~$13, Secrets Manager ~$11,
public IPv4 ~$7, WAF ~$9, fck-nat + bastion (t4g.nano each) ~$7, CloudWatch logs and the rest ~$10. `staging-power.sh stop`
brings it to about $70/month. Earlier choices: a managed NAT gateway (+$33) and Container Insights (+$10-15) were dropped
for staging.

Database access: `scripts/db-tunnel.sh` (SSM port forward through the bastion; see the script header).

## Production (`envs/production`)

Home region eu-west-2 runs the API, workers, Redis, edge and the `global` + `uk` databases. Eu, us, asia and africa each get
their own VPC, Postgres, uploads bucket and ClamAV (behind an internal NLB), peered to the home VPC. See `ARCHITECTURE.md`.

Before the first plan:

- **Separate production AWS account**, with `bootstrap/` applied in it.
- **Enable `af-south-1`** in that account (Billing > Account > AWS Regions). It is opt-in; plan fails until it is on.
- **Domain:** the apex zone `tryopenhr.com` is created here. After applying, set the printed nameservers at the registrar.
  Staging's sub-zone is delegated by passing its nameservers in `staging_name_servers`.

Order:

1. `cd envs/production`, `cp backend.hcl.example backend.hcl`, `cp terraform.tfvars.example terraform.tfvars`, `terraform init -backend-config=backend.hcl`.
2. `terraform apply -target=module.dns`, set registrar nameservers, wait for propagation.
3. `terraform apply` with `services_enabled = false`. Creates ~5 RDS instances (10-20 minutes), peering, buckets, certificates, edge.
   If the Africa fck-nat or any satellite fails, read the error: opt-in regions are the usual suspect.
4. **Mirror the ClamAV image once** into the home ECR so it replicates to the four satellites:
   `docker pull --platform linux/amd64 clamav/clamav:1.4`, tag it `<account>.dkr.ecr.eu-west-2.amazonaws.com/openhr/clamav:1.4`, push.
   Then confirm the image exists in each satellite region's ECR before enabling services.
5. Set secret values (same list and approach as staging; five `ANGLEHR_<REGION>_SENSITIVE_KEYS`, back them up).
6. Complete the changes in `CODE_CHANGES.md`, push images, run the migrate task (it reaches all six databases over peering),
   then `services_enabled = true` and apply.

Cost: very roughly **~$640/month** before traffic. ClamAV (five scanners at 1 vCPU / 3 GB, ~$45 each) is the largest
single item; the home NAT, ALB, five RDS instances and four NLBs make up most of the rest. Check the AWS calculator.

Choices still open (variables, no code change needed): `home_db_multi_az` (default false; the global registry and auth live
on that instance), `api_desired_count` (default 1), `home_nat_mode`.

Note for both stacks: `desired_count` is managed by Terraform, so an apply restarts staging services even if you stopped them
with the script (the DB stays stopped; run `stop` again).
